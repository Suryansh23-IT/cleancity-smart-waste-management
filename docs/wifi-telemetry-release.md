# CleanCity USB and Wi-Fi release runbook

Local operation uses the existing ESP32 serial diagnostics, Node receiver and SQLite. The Physical IoT Lab defaults to USB on loopback. The firmware can also send the same four diagnostics in a separate Wi-Fi task. The hosted Lab defaults to Wi-Fi and reads Atlas through the municipal operator session. Each view and each frozen snapshot uses one selected feed. The six virtual bins and approved 90 × 60 cm board retain their existing configuration.

## Preview and production configuration

1. After approval, link the repository to the intended Vercel project. Use the existing Vite build and Node API adapter. Git-triggered deployments are disabled in `vercel.json`. From an authenticated Vercel CLI, use `vercel` for the approved preview and reserve `vercel --prod` for the approved production launch.
2. Set server-side variables for each environment. Use `MONGODB_URI`, `MONGODB_DATABASE`, `APP_ORIGIN` (the exact HTTPS origin used in the browser), `OPERATOR_USERNAME`, `OPERATOR_PASSWORD_HASH`, and `WORKSPACE_ID`. Use separate preview and production databases or credentials with read/write and index access restricted to the intended database. Generate the production hash with `npm run --silent auth:hash` and a strong password over stdin.
3. Confirm a permitted network path from the selected Vercel runtime to Atlas before setting production secrets. Confirm the Vercel plan's egress options and request separate approval for any paid egress or Atlas access-list change. Validate `/api/health` and `/api/ready` through the preview domain. For a protected preview, confirm the hardware can reach the device endpoint under the approved protection policy.
4. For Wi-Fi, generate a high-entropy token locally. Keep the raw token in the ignored firmware `secrets.h`, and set its lowercase SHA-256 hash as `CLOUD_DEVICE_TOKEN_HASH` in Vercel. Set `CLOUD_DEVICE_ID` to the same device ID as the firmware. Use a separate preview database and a `device-test-` ID for fixtures. The server labels that feed and its snapshots TEST. Configure measured per-channel `CLOUD_DEVICE_CALIBRATION` only after physical checks. Omit it for distance-only operation. Legacy Supabase settings are unnecessary for this path.
5. Apply a Vercel Firewall rate rule to `POST /api/session` and a separate rule to `POST /api/telemetry/ingest` before public launch. Begin with 8 login attempts per 15 minutes per client IP and 30 ingest attempts per minute per client IP, then test the configured policy. Return 429 and verify that normal device traffic succeeds. The app enforces an 8 KiB device body limit and Atlas enforces one stored batch per device per five-second window across instances. The app's in-process login limiter is an additional local control. [Vercel Firewall rules](https://vercel.com/docs/vercel-firewall/vercel-waf/custom-rules)
6. On the preview, verify deep API routing, secure cookies, Origin/CSRF rejection, invalid device credentials, valid device ingestion, retries and storage restart, and the operator-only snapshot endpoint. Check real browser workflows, the target browser and phone, and the Vercel request/response ceiling with representative large cities. Verify runtime logs and alerts for 5xx, Atlas connectivity and throttling. Log request IDs and status, and keep authorization headers, payloads and database URLs out of logs. Record the tested commit and previous deployment before production and verify rollback and database recovery. [Vercel runtime limits](https://vercel.com/docs/functions/limitations)

## Telemetry contract and operations

- `POST /api/telemetry/ingest` accepts one JSON object with `deviceId`, random 32-hex `bootId`, integer `seq`, `sampledAtMs`, and four `readings`. Each reading has its fixed `binId`, `pulseUs`, `beforeHigh` and `afterHigh`. The bearer token authenticates the configured device. Stable batch identity uses workspace, device, boot and sequence. Retries preserve the original timestamp and payload.
- The firmware keeps one pending batch, samples the Wi-Fi feed at most every 10 seconds and discards old observations. Its bounded background retry loop leaves the USB sensor loop independent. The API rejects invalid mappings or implausible timestamps, records server receipt time and derives distance using the same pulse formula as USB. A valid distance without measured calibration stays distance-only.
- `GET /api/telemetry/snapshot` returns latest and up to 30 recent batches per channel to the operator workspace. The Lab marks Wi-Fi readings stale after 45 seconds and the feed offline after two minutes without a recent sample. The Atlas `iot_observations` collection uses seven-day TTL plus deduplication and rate-window indexes. Monitor Atlas storage and transfer usage during sustained demonstrations. [Atlas Free cluster limits](https://www.mongodb.com/docs/atlas/reference/free-shared-limitations/)
- If Wi-Fi or Atlas is unavailable, select USB in the local app. If the firmware or cloud endpoint regresses, roll back to the previous known-good build and retain municipal and telemetry records. Revoke a leaked device token by replacing its hash and securely updating the firmware.

## Local verification

- The automated suite passed 181 tests, with one opt-in disposable-database test skipped. It covers existing routes and playback, USB parser/SQLite behavior, device and operator authorization, oversized and invalid readings, duplicates, rate limits, and stale or invalid snapshot input.
- Real development Atlas passed controlled connection refusal and recovery, municipal authentication and persistence, and TEST telemetry storage and duplicate retry. The browser passed save, refresh, resume and history read-back, plus the Wi-Fi TEST snapshot through Dispatch, Simulation and Analytics. An isolated 390 px browser switched back to USB without carrying Wi-Fi readings into the local view. All seven screens also opened in a separate local smoke run.
- TypeScript, Vite production build and the municipal Node handler bundle passed locally. The routing sample ran 12 iterations per scenario. The 100-bin Westhaven plan took about 4.85 ms at the sampled p95 on this computer.
- Arduino ESP32 core 3.3.12 compiled the USB-only sketch and the Wi-Fi sketch with nonsecret compile settings for ESP32 Dev Module. The Wi-Fi binary used 78% of the default application partition. These checks establish software and firmware compilation. Hosted routing, production networking and actual calibrated ESP32 readings remain acceptance gates.
